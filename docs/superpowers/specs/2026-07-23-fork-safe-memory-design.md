# Fork 安全的分支记忆设计

## 目标

用户在任意旧消息处创建 SillyTavern 分支后，新分支只继承分叉点以前成立的记忆，父分支和子分支随后独立演化。恢复未完成或失败时不得注入可能串线的记忆。

## 已确认的宿主行为

SillyTavern 创建分支时复制分叉点以前的消息，只给新聊天写入 `main_chat` 父聊天名，不复制第三方扩展的聊天元数据。新聊天加载完整消息和元数据后触发 `CHAT_CHANGED`。消息 `extra` 中的 `layered_memory_id` 会随消息快照保留。

## 数据模型

- `floor_events`：每轮提取后的不可变事件，包含稳定 `floorKey`、轮次、完整的受影响条目终态和每轮摘要。相同楼层重新生成时替换该楼层事件。
- `branch_checkpoints`：状态表检查点，绑定创建时最后一条已封存对话的稳定 `floorKey`。首次升级、手动修改和状态表整理后生成；同一锚点只保留最新检查点。
- `branch_origin`：记录父聊天、恢复方式、分叉点和恢复时间，供诊断显示。

检查点解决升级前已有状态、手动操作和状态表整理不可逆的问题；楼层事件负责从最近可用检查点确定性重放后续自动变化。

## 分支恢复

1. `CHAT_CHANGED` 后，如果当前聊天带 `main_chat` 且没有插件数据，进入恢复屏障。
2. 通过 SillyTavern `/api/chats/get` 或 `/api/chats/group/get` 读取父聊天头部的插件元数据。
3. 用新分支实际包含的稳定消息 ID 计算有效 `floorKey` 集合。
4. 选择锚点仍存在于分支中的最新检查点，从该状态开始，按轮次重放锚点之后且仍存在的 `floor_events`。
5. 每轮摘要按 `floorKey` 过滤；只复用完整落在分支范围内的章节；卷摘要只有在其全部章节都保留时才复用，否则重新排队生成。
6. 待确认项只保留仍存在楼层产生的项目。后台队列一律清空并生成新的 `scope_id`。
7. 父数据只读，新分支保存独立副本。

若没有可用检查点（主要是升级前很早的位置），使用兼容恢复：复制父状态并依据完整 changelog 回滚分叉点后的逐层变化，同时标记为 `legacy_rewind` 并排队校对。该路径不宣称字节级完全重放，但不得包含已能识别为分叉点之后的逐层摘要、章节、卷和任务。

## 生成屏障与失败处理

- 初始化、`CHAT_CHANGED`、消息事件和生成拦截器共享同一个恢复 Promise。
- 恢复完成前不更新注入；生成拦截器等待恢复结束。
- 父聊天读取或保存失败时，清空新分支注入，写入显眼的恢复失败提示，不用父分支当前记忆继续生成。
- 重复进入已经恢复的分支必须幂等，不再次复制或重放。

## 验收矩阵

- 单聊与群聊。
- 从用户消息、AI 回复、章节中间创建分支。
- 分支点位于检查点之前和之后。
- Fork 时任务正在运行或等待重试。
- 连续 Fork，父子分支来回切换，父分支之后继续产生新记忆。
- 恢复期间立即发送消息。
- 父聊天缺失、接口失败和保存失败时必须 fail closed。

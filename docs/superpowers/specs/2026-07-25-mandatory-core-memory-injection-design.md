# 核心记忆必选注入设计

## 问题

L1 当前事实和 L2 剧情摘要目前通过 `IN_CHAT + depth` 注入。SillyTavern 会把这类内容放进聊天历史候选池，再从最新消息向旧消息消耗剩余预算。深度较大的注入位于旧历史一侧，在上下文缩小时可能与旧聊天一起消失；预设中的绝对注入还会改变实际排列，因此固定 depth 不能提供可靠保证。

## 选择

将 L1 和 L2 改为 `IN_PROMPT` 的 system 扩展提示词，并为 API 的 depth 参数传入不参与定位的 `0`。SillyTavern 会把它们放到 main 提示词集合末尾，先从提示词预算中扣除，再用剩余预算填充聊天历史。

L4 相关旧记忆继续使用 `IN_CHAT + depthL4`，因为它是临时检索结果，靠近当前对话的位置仍有意义，也允许在容量紧张时被舍弃。

未采用的方案：继续调整固定 depth，无法避开预设绝对注入和预算变化；将 L1/L2 拼成一个新 key，会增加迁移和清除旧 key 的复杂度，而两个现有 key 分别改为 `IN_PROMPT` 已能获得相同的必选预算语义。

## 设置兼容

界面移除 L1/L2 的发送位置输入框，因为它们不再影响行为。已有 `depthL1`、`depthL2` 设置保留在存量配置和默认结构中，不主动删除，避免不必要的数据迁移；保存设置时也不再改写它们。L4 的发送位置设置保持不变。

## 失败行为

如果 main 提示词、L1 和 L2 的总量已经超过请求预算，沿用 SillyTavern 的 mandatory prompt 超限错误。不得退回 `IN_CHAT` 或静默省略核心记忆。

## 验证

- 单元契约捕获 `setExtensionPrompt` 调用，断言 L1/L2 为 `IN_PROMPT`、system、depth 占位值 `0`。
- 同一测试把旧 `depthL1`、`depthL2` 改成非默认值，证明它们不再影响注入。
- 断言 L4 仍为 `IN_CHAT` 并采用 `depthL4`。
- 运行仓库完整测试，并检查界面中只剩 L4 发送位置。

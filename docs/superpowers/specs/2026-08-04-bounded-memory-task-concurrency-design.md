# 有限并发记忆任务设计

## 目标

缩短一批互不依赖的后台模型任务的总等待时间，同时继续保证同一聊天的事实状态、任务恢复和最终提交不会发生竞态。任务面板必须分别显示正在处理与等待处理的数量，不能把未完成总数描述成并发数。

## 并发边界

同一聊天最多同时运行 3 个任务。只有下列结果按稳定楼层或不重叠区间写入、且可按楼层重新排序的任务允许同类并发：

- `narrative_summary`
- `narrative_chapter`
- `chapter_summary`
- `history_rebuild_segment`
- `history_rebuild_chapter`
- `extract` 的模型分析阶段

每批只运行同一种可并发任务。这样逐楼记录全部完成前不会提前运行章节任务，章节全部完成前也不会提前运行最终提交。

实时 `extract` 拆成两个阶段：先用领取任务时的事实表并发请求模型，再按任务领取顺序逐条校验、合并和保存。提交时必须使用最新事实表；如果预分析结果因更早楼层改变了同一事实而全部失效，只在自己的提交位置重新请求这一楼，然后再允许后续楼层提交。

迁移提取、校对、状态去重、卷压缩和最终提交继续独占队列。它们会跨范围修改共享状态，或本身已经包含内部顺序，不能直接加入工作池。

## 队列与持久化

- 内存中的单个 `inFlight` 改为运行任务集合；快照同时提供 `running` 数组和兼容旧调用的首个 `inFlight`。
- `chat_metadata.layered_memory.job_queue.running` 从单个对象迁移为数组。加载旧数据时将旧对象自动包装成数组；刷新后把所有未完成运行任务重新排队。
- 暂停只阻止领取新任务，已经发出的模型请求安全完成。
- 切换聊天时，旧聊天任务失去保存权限；返回原聊天后从持久状态恢复。
- 插件发起的聊天元数据保存串行执行，避免多个并发任务同时调用保存接口。

## 调度规则

1. 若有独占任务运行，不领取其它任务。
2. 若有可并发任务运行，只补充相同任务类型，直到达到 3 路。
3. 队列空闲时，以最高优先级的就绪任务决定下一批；独占任务只领取一个，可并发任务领取同类型最多三个。
4. 重试延时、三次尝试、去重和失败任务人工处理规则保持不变。

## `extract` 提交序列

- 每个任务在发出模型请求前预留一个提交位置，位置顺序与队列领取顺序一致。
- 模型请求不等待前一个任务，因此最多三楼可以同时请求。
- 模型返回后等待自己的提交位置；等待期间不修改聊天元数据。
- 轮到自己时重新读取当前事实表并执行原有 evidence、实体、`old_value` 和冲突校验。
- 首次结果若没有任何事实被采用且存在被丢弃项，使用最新事实表重算一次；第二次结果沿用现有降级与失败规则。
- 无论成功、失败还是切换聊天，都必须释放提交位置，避免后续任务永久卡住。聊天切换后的任务仍由持久队列恢复。

## 界面

任务面板渲染所有实际运行任务。存在运行与等待任务时，摘要使用“共 N 项：X 项处理中，Y 项等待”；失败数量单独列出。设置页的开发者统计也使用真实运行任务数。

## 验收

- 三个安全任务能够在第一个任务完成前同时进入处理器，第四个保持等待。
- 三个实时 `extract` 的模型请求能够重叠；即使后楼先返回，事实合并、`turn_summaries` 和完成日志仍按领取顺序发生。
- 后楼预分析引用的旧事实被前楼改变时，只重算后楼一次，并采用重算后的结果。
- 独占任务不会和其它任务重叠；不同并发任务类型不会跨阶段混跑。
- 暂停、失败重试、旧版单个 `running` 恢复、聊天作用域隔离继续有效。
- UI 对 1 个运行、7 个等待显示“共 8 项：1 项处理中，7 项等待”。
- 完整测试套件通过。

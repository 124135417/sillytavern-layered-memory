# 按可见楼层注入剧情记忆

## 已确认的问题

SillyTavern 页面上的一“楼”是一条消息；现有插件却把一组用户消息与角色回复组成的 `pairIndex` 当作一楼。于是配置中的“每 25 楼一章”实际变成了约 50 个可见楼层一章。第 44 楼附近只会得到约 22 条配对摘要且没有章节，无法满足预设关闭上下文后由插件独立交付完整前情的要求。

## 产品契约

- 剧情连续性使用 SillyTavern 的真实消息序号：初始角色消息是第 0 楼，之后每条用户或角色消息各占一楼。
- 每个已经完成的历史楼层都有一条独立小摘要。当前正在生成所对应的末尾用户消息仍由主提示原文提供，不重复注入为摘要。
- 从第 0 楼开始，每连续 25 楼冻结为一个章节。章节存在时替代同范围的逐楼摘要；未满 25 楼的尾部逐楼注入，不能留洞、不能重复覆盖。
- 因而生成第 44 楼时，历史范围由第 0–24 楼的一章、第 25–42 楼的 18 条小摘要，以及仍在主提示中的第 43 楼用户原文共同构成；从“历史共 44 楼”的视角看就是 25 + 19，且没有任何一楼失踪。第 44 楼生成完成后，下一次注入应是第 0–24 楼一章加第 25–44 楼 20 条小摘要。
- 注入继续由预设中的 `{{layered_memory_context}}` 精确锚定；本改动不替代预设、不改变宿主提示角色或顺序。

## 数据边界

现有 `turn_summaries`、`floor_events`、事实表和提取键继续按 user+assistant 配对工作，用于持久事实验证与 Fork 重放。新增独立的剧情连续性材料：

- `narrative_summaries`：按稳定消息 ID 保存消息楼层、角色、正文指纹和小摘要。
- `narrative_chapters`：仅覆盖连续的真实消息楼层，范围固定为 0–24、25–49 等。

这样修正剧情颗粒度时不会改写既有事实来源、冲突处理或检查点。旧的配对章节不再参与剧情注入；它们仍可供现有事实校对和旧版界面使用。

## 生成与恢复

- 后台按批次补齐缺失的逐楼摘要，一次模型调用返回多楼结果并逐项校验楼号、数量和长度。
- 新消息、刷新、聊天切换、编辑、删除和 swipe 后都按稳定消息 ID 与正文指纹重新核对：相同材料复用，改变或消失的材料不复用。
- 若后台摘要尚未完成，注入用该楼正文的有界临时记录补位，保证剧情覆盖不突然归零；模型摘要完成后原位替换。
- 只有 25 条已校验的小摘要齐全时才生成对应章节。章节失败时继续注入这 25 条小摘要，不丢剧情。
- Fork 只继承当前分支中真实存在、ID 与正文指纹均匹配的逐楼摘要；不匹配的部分重新生成。

## 注入顺序

`<前文回顾>` 锚点内保持：长期/章节/逐楼剧情（按真实楼层升序）在前，当前仍成立的结构化事实在后。每段有明确开始、结束和楼层范围，后续预设提示与当前用户输入不属于任何摘要段。

## 验收

自动化测试至少证明：

1. 44 个历史消息时输出 1 个第 0–24 楼章节、19 个第 25–43 楼小摘要，且章节覆盖范围内的小摘要不重复。
2. 当前末尾是用户消息时，该消息不被摘要重复注入；前面的历史楼层无缺口。
3. 修改正文、删除消息或切换 swipe 后，旧指纹材料不会跨分支复用。
4. 旧聊天没有 `narrative_summaries` 时会自动补齐，不需要清空现有事实或让用户重新执行安全重建。
5. 最终以线上当前聊天的“查看输入”为准，确认宏已展开、宿主位置和 Assistant 角色未变、剧情范围符合真实楼层。

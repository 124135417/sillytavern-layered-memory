## 0. 问题陈述（为什么要做）

SillyTavern（下称 ST）长程角色扮演（600+ 楼）存在两个互相矛盾的问题：

1. **Context 爆炸**：全量历史原文注入，token 随楼数线性增长，最终超出模型窗口或成本不可接受。
2. **记忆崩坏**：常见缓解方案是"滚动摘要"（每楼生成摘要、旧摘要不断被重写合并）。摘要被反复转述几百次后误差累积（传话游戏效应），六七百楼时人物设定、关系、剧情因果、背景事实出现可感知的漂移与崩坏。

已有的"记忆表格"类插件失败的根本原因（必须避免重蹈）：

- 让 RP 主模型在演戏的同时顺便填表 → 输出端污染，填表敷衍、乱填；
- 提取指令是开放式价值判断（"记录重要内容"）→ 模型的重要性判断不可靠，漏记与乱记并存；
- 没有"不填"的显性正确答案 → 模型倾向每次都填点什么；
- 不要求证据、代码层照单全收 → 编造内容直接入表；
- 作者从未量化评测提取质量 → 全靠玄学调 prompt。

**核心设计原则**（全文反复引用，编号 P1–P6）：

- **P1 分层**：不同性质的信息走不同通道，互不替代。状态表管"事实正确"，摘要管"因果连贯"，近楼原文管"此刻鲜活"，检索管"按需细节"。
- **P2 写一次冻结**：任何摘要只经历有限次（≤2 次）有损压缩，绝不滚动重写。
- **P3 检测题不是品味题**：提取用封闭槽位（"有没有人受伤？"），不问开放判断（"什么重要？"）。
- **P4 模型写字、代码验收**：所有模型输出必须过机械校验（证据引文、实体存在性、enum 合法性、长度上限），失败即丢弃。丢弃是安全的，因为有下层兜底。
- **P5 降级不销毁**：压缩=从常驻 context 降级为按需检索，原文永远在磁盘。任何一层漏了，下层可捞（漏记 → 延迟收录，而非永久丢失）。
- **P6 一切有硬上限**：每轮注入的每一层都有固定 token 预算，总量与总楼数无关。

## 1. 系统总览

### 1.1 五层记忆结构

| 层 | 内容 | 更新方式 | 常驻 context？ | token 预算（默认） |
|---|---|---|---|---|
| L0 静态设定 | 角色卡 / 世界书 / persona | ST 原生，插件不管 | 是 | ST 原生控制 |
| L1 状态表 | 持久事实的当前真值 | 每楼异步 diff 合并 | 是 | 2000 |
| L2 摘要层 | 卷摘要 + 章节摘要（因果链） | 每 25 楼冻结新增；触顶时卷压缩 | 是 | 5000 |
| L3 近楼原文 | 最近 N 楼完整原文 | 滑动窗口 | 是 | N=3 楼（按楼数不按 token） |
| L4 检索层 | 命中的旧章节摘要/原文片段 | 关键词触发，按需注入 | 仅命中时 | 1500 |

磁盘归档（不进 context）：全部楼层原文、全部历史章节摘要、状态表变更日志。

### 1.2 调用拓扑

```
用户发消息
  ├─ [同步] 组装 context（纯代码，见 §6）→ 调 RP 主模型 → 流式返回回复
  └─ 回复落地后：
       ├─ [异步] 每楼：提取调用（见 §3）→ 校验 → 合并进状态表
       ├─ [异步] 每 25 楼：章节摘要调用（见 §4.1）→ 冻结入库 + 抽关键词入索引
       ├─ [异步] L2 触顶时：卷压缩调用（见 §4.2）
       └─ [异步] 每 50–100 楼：校对 pass（见 §5）→ 建议进待审列表
```

**用户唯一等待的调用是 RP 主生成**。其余全部在用户阅读/打字的间隙后台执行。提取未落地时下一楼用旧表——一轮延迟无害（近 3 楼反正是原文）。

### 1.3 模型分工

- **RP 主模型**：用户自选（写文强的模型）。只负责"演"。**绝不**在它的输出里要求任何结构化内容。
- **提取/摘要/校对模型**：独立配置，建议便宜且指令服从性好的模型（如 Haiku 级）。所有调用使用**干净上下文**：system 里只有任务指令 + schema + few-shot，**不含**角色卡、越狱、文风指令。

## 2. 状态表（L1）

### 2.1 定位

状态表**不存事件，存事件的残留物**——很久以前确立、现在仍然为真、但近楼原文中不会出现的事实。

- 存："A 与 B 关系：冷战中（因第 320 楼书房争吵）"
- 不存："第 320 楼两人大吵一架"（这是事件，归 L2）
- 不存：实时状态（此刻在哪/什么姿势/情绪）——近 3 楼原文已覆盖
- 不存：角色卡里写死的静态设定——L0 已全量注入

判断标准一条：**近期原文里找不到、但写错会崩人设/崩剧情的事实**。

### 2.2 数据结构

```jsonc
// state_table.json
{
  "version": 3,                    // 每次合并 +1
  "entries": [
    {
      "id": "e_0012",
      "slot": "relationship",      // 见 §2.3 槽位 enum
      "subject": "艾琳",            // 主实体
      "object": "卡尔",             // 可空
      "value": "冷战中",
      "cause": "书房争吵",          // 简短成因，可空
      "established_floor": 321,    // 确立楼层
      "updated_floor": 321,        // 最后更新楼层
      "evidence": "\"我不想再看到你。\"",  // 确立时的原文引文
      "pinned": false,             // 用户钉住则任何自动流程不得修改
      "source": "auto"             // auto | manual | proofread
    }
  ],
  "changelog": [ /* 每次 diff 合并的记录，追加式，用于回滚与 eval */ ]
}
```

### 2.3 槽位定义（六个检测槽 + 一个兜底槽）

| slot | 检测问题（封闭式） | value 示例 |
|---|---|---|
| `promise` | 本楼有人许诺/立约/定期限了吗？ | "答应三日内归还长剑" |
| `body` | 有人身体状态**永久**改变了吗（伤/疤/能力得失）？ | "左臂留下刀疤" |
| `relationship` | 关系**定性**变了吗（敌↔友、隐瞒↔坦白、在一起↔分手）？ | "信任 → 冷战" |
| `identity` | 身份/秘密揭露了吗？ | "实为北境卧底" |
| `possession` | 关键持有物变更了吗（获得/失去/损毁/转赠）？ | "获得母亲的银坠" |
| `world` | 产生新的**世界事实**了吗（某地陷落、某规则被验证）？注意：仅限扮演中**新产生**的，卡里写死的不算 | "王都已陷落" |
| `other` | 兜底槽：确立了不属于以上、但**会持续为真**的事实吗？必须额外说明为何持久 | — |

每个槽位的合法输出是二选一：`"无变化"` 或 一条/多条具体条目。**"全部无变化"是常见且正确的答案**（见 §3.3 few-shot 要求）。

### 2.4 更新语义：diff，不重写

提取调用输出的是相对当前表的**变更集**，三种操作：

```jsonc
{ "op": "add",    "entry": { ...新条目... } }
{ "op": "update", "id": "e_0012", "value": "和好", "cause": "雨夜道歉", "floor": 402 }
{ "op": "flag_conflict", "id": "e_0007", "note": "表称A在北方，本楼A出现在王都" }  // 仅标记，进待审列表，不自动改
```

代码合并规则：`add` 查重（同 slot+subject+object 视为重复 → 转 update）；`update` 保留旧值进 changelog；`pinned=true` 的条目拒绝一切自动 op。**状态表容忍冗余**——多录细枝末节无害（一条 ~15 token，定期整理即可），漏录才有害，而漏录有 §4/§5/§8 三道补网。

## 3. 提取管线（每楼一次，异步）

### 3.1 调用输入（严格限定，缺一不可、多一不许）

```
system:
  [提取任务指令]（见 §3.3）
  [槽位 schema 定义]
  [few-shot 示例 ×4]
user:
  [当前状态表（渲染为紧凑列表）]      ← diff 是相对概念，无基准无法判断"变化"
  [本楼用户输入原文]                 ← 用户动作同样改变事实（如送出信物）
  [本楼 AI 回复原文]
```

**禁止**输入：角色卡、越狱、文风指令、历史楼层（连续性由状态表承载，不需要提取调用看历史；上下文里每个多余 token 都在稀释任务）。

参数：`temperature=0`，输出强制 JSON（有 structured output 能力就用）。

### 3.2 输出 schema

```jsonc
{
  "promise":      "无变化" | [ { "subject","object","value","evidence" } ],
  "body":         "无变化" | [ ... ],
  "relationship": "无变化" | [ { "subject","object","old_value","new_value","evidence" } ],
  "identity":     "无变化" | [ ... ],
  "possession":   "无变化" | [ ... ],
  "world":        "无变化" | [ ... ],
  "other":        "无变化" | [ { "subject","value","why_persistent","evidence" } ],
  "conflicts":    [] | [ { "entry_id","note" } ]
}
```

### 3.3 提取指令要点（prompt 必须包含的要素）

1. 明确身份："你是事实记录员，不是作者。只记录**已在文本中明确发生**的持久变化，不推测、不补完、不评价重要性。"
2. 逐槽提问（检测题形式），强调：**输出"无变化"是完成任务，不是偷懒**。
3. **证据强制**：每条目必须附 `evidence` = 原文中的直接引文（≤50 字）。引不出原句就不许填。
4. few-shot ×4，其中**至少 2 个示例的正确答案是全部"无变化"**（例如一段纯闲聊/纯战斗描写但无持久后果的楼层）。这是压制乱填率的最关键单点。
5. `other` 槽必须给出 `why_persistent`，说明该事实为何会持续为真而非一次性事件。

### 3.4 代码层校验（P4，全部机械规则）

按序执行，任一失败 → 整条目丢弃（不是整个 diff 丢弃）：

1. `evidence` 必须是本楼原文的子串（做空白归一化后匹配）；
2. `subject`/`object` 实体名必须在本楼原文或当前状态表中出现过；
3. `slot` / `op` 必须是合法 enum；
4. 单条 `value` ≤80 字（防止把剧情摘要塞进槽位）；
5. 校验失败的条目允许**重试一次**（把失败原因附在重试 prompt 里），再失败即丢弃并记日志。

丢弃是安全的：该事实仍在 L2 章节摘要里（章节摘要是连续叙述，不经槽位过滤），可被 §5 校对 pass 或 §2.2 提及统计事后捞回（P5）。

## 4. 摘要层（L2）

### 4.1 章节摘要（每 25 楼一次，写完冻结）

触发：第 25/50/75… 楼的提取完成后追加一个异步调用。

输入：该 25 楼的完整原文（+ 上一章摘要的最后两句，仅用于衔接语气）。
输出：

```jsonc
{
  "summary": "~300字连续叙述，重点保留因果链（因为X所以Y）与事件顺序",
  "keywords": ["实体名1", "物品名2", ...],   // 3–10 个，用于 L4 检索索引
  "floor_range": [126, 150]
}
```

规则：

- **写完即冻结，永不重写**（P2）。用户可手动编辑，编辑后同样冻结。
- 原文 25 楼归档磁盘，退出 context。
- `keywords` 自动生成为检索索引条目（等价于自动世界书条目，见 §7）。
- 摘要要求保留**因果与转折**，禁止只罗列事件（"A做了X，B做了Y"是不合格输出；"因为A做了X，B才Y"是合格输出）。

### 4.2 卷压缩（L2 触顶时触发）

触发条件：L2 全部摘要渲染后 > 5000 token 预算。

流程（三步，代码主导）：

1. **代码生成"必须保留清单"**：对将被压缩的最老 8–10 章，统计——
   - 章内实体在**后续**章节/楼层的提及次数（提及≥3 次的实体入清单）；
   - 与状态表条目关联的事实（已入表的可不入清单——真值在表里，压丢无害）；
   - 用户钉住（`pinned`）的章节**整章排除**在压缩之外。
2. **AI 调用**：输入 8–10 份章节摘要 + 必须保留清单 → 输出一份 ~400 字卷摘要。
3. **代码验收**：清单中每个实体必须出现在输出中，缺失 → 重试一次（附缺失列表），再失败 → 本次压缩中止、报警给用户（宁可暂时超预算，不接受静默丢失）。

压缩后：原章节摘要**降级**——退出 context，但保留在磁盘且检索索引仍指向它们（P5）。

层级封顶：原文 → 章节摘要（第 1 次有损压缩）→ 卷摘要（第 2 次）。**不存在第 3 次**——卷摘要数量增长是对数级的（700 楼≈2–3 卷 + 8–10 章），如极端长局导致卷摘要也触顶，允许"卷的卷"但必须同样走清单+验收流程（实践中数千楼内不会触发）。

## 5. 校对 pass（每 50–100 楼，异步，人工批准）

目的：垃圾回收——捞提取漏掉的，纠表内错的。

输入：当前状态表 + 最近 2–4 份章节摘要。
提问（仍是封闭式）：

1. 这些摘要中涉及的实体/持久事实，状态表里有对应条目吗？缺哪条？
2. 表中条目与摘要有矛盾吗？

输出：建议列表（add/update/flag），**全部进入 UI 待审列表，用户批准才生效**——这是系统里唯一会"改旧账"的自动流程，保留人工闸门。

## 6. Context 组装（每楼同步，纯代码）

拼装顺序（自上而下）：

```
[L0 角色卡 / 世界书 / persona]          ← ST 原生
[L1 状态表渲染块]                       ← ≤2000 token
[L2 卷摘要（旧→新）+ 章节摘要（旧→新）]   ← ≤5000 token
[L4 检索命中块（如有）]                  ← ≤1500 token
[L3 近 3 楼完整原文]
[用户本轮输入]
```

### 6.1 L1 渲染模板

状态表不注入 JSON，渲染为分节自然语言：

```
## 当前确立的事实
以下是先前剧情中确立、至今仍然为真的事实。生成时必须与之保持一致，
但不要主动复述或提及本列表的存在。

### 承诺与约定
- 艾琳答应三日内归还长剑（第210楼起）
### 身体状态
- 卡尔左臂有刀疤（第50楼受伤所致）
### 关系
- 艾琳↔卡尔：冷战中（因书房争吵，第321楼起）
...（空分节省略）
```

尾注"不要主动复述"是防"念设定"的关键包装词。

### 6.2 L4 检索命中渲染模板

```
## 背景参考（可能相关的过往剧情）
仅当与当前对话直接相关时才使用以下内容；若无关，完全忽略，不要主动提及。

- [第126–150楼] <命中的章节摘要全文>
```

### 6.3 预算执行

- L1 超 2000：触发状态表整理调用（合并同类、删除被 update 链取代的冗余），仍超则最旧的低频条目降级归档；
- L2 超 5000：触发 §4.2 卷压缩;
- L4 超 1500：按命中得分截断到预算内;
- 每轮总注入量恒定，与总楼数无关（P6）。

## 7. 检索层（L4，关键词触发，可选组件）

**明确定位：锦上添花，不是系统成立的前提**。L1+L2 已完成"防崩"；L4 只负责偶尔捞细节。第一版可以不实现，或实现后默认关闭。

- **不用 embedding**（向量召回噪音大、误命中后模型硬提——"煎饼问题"）。用**词法匹配**：索引 = 所有章节摘要的 `keywords` → 章节摘要（及其楼层区间原文）的倒排表。
- 触发：组装 context 时，对**用户本轮输入 + 最近 1 楼**做关键词扫描（精确匹配 + 可选简单别名表）。
- 三道闸门：top-k=3 硬上限；1500 token 预算截断；**零命中零注入**（宁缺毋滥）。
- 命中注入的是章节摘要；若用户点开要求细节，可二跳取该章归档原文的对应段落。
- 已知局限（如实告知用户，不试图解决）：**隐性回调**（当前文本没出现关键词、但情境上应唤起旧剧情）抓不到。后果是"错过加戏机会"而非"说错事实"——防崩不依赖本层。

## 8. 用户界面

侧边栏面板（ST extension 标准 drawer），四个区：

1. **状态表视图**：按槽位分节展示全部条目；刚被 diff 更新的条目高亮 3 秒；每条可编辑/删除/**钉住**（钉住=禁止一切自动修改）；顶部"+"手动加条目（`source:"manual"`）；**报错按钮**——用户发现记忆错误时点击，选类型（漏了/乱填/填错）+ 写一句正确答案，自动生成 §10 错例（存该楼原文 + 当时状态表 + 期望输出）。
2. **章节列表**：每章显示楼层区间+摘要，可展开编辑（编辑后冻结）、可**钉住整章**（排除出卷压缩）。
3. **待审列表**：校对 pass 与 `flag_conflict` 的建议，逐条 批准/驳回。
4. **设置**：提取模型/主模型分离配置、各层 token 预算、章节大小（默认 25）、校对周期、卷压缩自动/需确认开关、L4 开关。

设计立场：**全自动模式下用户可以永远不打开面板**；面板是最终兜底（人比任何算法可靠，长线 RP 玩家愿意付出这个成本）。

---

## 9. 存量迁移（冷启动已有几百楼的旧局）

1. **回填章节摘要**：对历史每 25 楼跑 §4.1（有原文用原文；仅有旧滚动摘要的楼层用旧摘要替代）。700 楼 = 28 个异步调用，一次性成本。
2. **回填状态表**：对 28 份章节摘要**按时间顺序逐份**跑 §3 提取（输入=累积中的表+该章摘要），累积出当前状态表。
3. **人工校对一遍**：冷启动的表必须由用户过目修正——用户对自己的剧情比任何模型熟，一次人工投入换全自动地基干净。**迁移工具必须记录用户的每处修改**（漏的/乱填的/填错的），自动生成 §10 错例——迁移和评测是同一件事的两面。
4. 旧的每轮滚动摘要退役归档。**同时从 RP 预设中删除**：a) 每轮顺带生成摘要的指令；b) 摘要输出格式约束。保留预设中一切"怎么演"的部分。

## 10. 评测框架（实现质量的唯一标尺）

不建 eval 就会重蹈现有插件覆辙——但 eval **不要求前期人工标注**。

### 10.1 定位（先讲清楚这是什么）

golden set 是提取管线的**单元测试套件**，不是 ML 训练数据：

- 每条用例 = 该楼原文 + 当时的状态表 + 期望输出（"应提取什么"，多数情况为空）；
- 唯一用途是**跑**：改 prompt/换模型/调 schema 后重跑全集，对比输出与期望，报 pass/fail 与 precision/recall。回答"这次改动是进步还是退步"，提供回归防护；
- **永不进入任何模型的上下文**。修复回路是：错例聚类 → 人看出病灶规律（如"隐晦表达的关系变化漏检"）→ 人改提取 prompt 里的规则/类别定义 → 重跑验证。模型每次调用都是失忆的，改好靠规则被固化进 prompt，不靠模型"吸取教训"；
- 唯一例外：人工挑选个别典型错例，改写成提取 prompt 的 few-shot 示范（此时它是任务示范，不是历史批评）；
- 测的是**能力不是剧情**：用例考的是"含关系破裂的文本能否被检测"这类考点，跨题材复用。提取器的失败模式是收敛的（闲聊楼乱填、戏剧性事件误报、隐晦表达漏检、把事件当事实、编造细节），修好一类病 = 对所有剧情修好。新题材暴露新失败 → 新错例入集。

### 10.2 冷启动：错例收集箱模式（起步为空集，不阻塞开发）

1. **框架先行**：实现错例存储格式 + 重跑脚本即可，零标注开工。
2. **错例来源一（主）——迁移校对副产品**：§9 存量迁移时用户人工校对回填的状态表，用户改掉的每一处（漏/乱填/填错）由代码自动存为一条错例。迁移工具必须实现"用户修改 → 自动生成测试用例"的钩子。
3. **错例来源二——面板报错按钮**：运行期用户发现记忆错误时点一下，选类型（漏了/乱填/填错），写一句正确答案，自动入集。10 秒/次，发生在用户本来就要动手改表的时刻。
4. **可选种子集**：迁移前想冒烟测试，让用户挑 5 个关键楼（明确该记）+ 5 个闲聊楼（明确该空），共 10 条即可，不要求更多。

**明确不要做的**：不要求用户预先标注 50–100 楼；不要用编造的合成对话当测试数据（分布失真）；AI 辅助预标注时**绝不能**用被测的提取模型自己标（自己出题自己考测不出盲区）。

### 10.3 指标与取舍

1. **提取评测**：precision（填的里多少是对的）/ recall（该填的漏了多少）。**recall 优先**（冗余无害、漏才有害），目标参考：recall ≥0.9，precision ≥0.7。
2. **压缩评测**（有条件再做）：真实 25 楼 + "必保留要点清单"，量章节摘要的要点保留率。
3. 若改规则、加示范后某类错例仍然过不了 → 那是**模型能力天花板**信号：换更强的提取模型重跑错例集看值不值差价，或接受上限——架构本就不要求提取完美，漏检由 L2 摘要 + §5 校对 pass + 面板手补兜底。

## 11. 边界情况与已明确的取舍

- **提取比用户打字慢**：下一楼用旧表，无害（L3 原文兜住即时性）。
- **提取调用彻底失败**：跳过本楼，记日志。事实仍会进章节摘要，可被校对捞回。
- **卷压缩验收连续失败**：中止压缩、允许暂时超预算、面板报警。绝不静默丢。
- **世界书/角色卡与状态表冲突**：状态表只记"扮演中新产生"的事实；若确与 L0 冲突（剧情推翻了卡设），`flag_conflict` 进待审，由用户裁决。
- **多角色群聊**：条目的 subject/object 天然支持；章节摘要按楼数切，不按角色切。
- **槽位覆盖不了的新型持久事实**：`other` 槽 + 校对 pass + 手补。若某类事实反复靠手补，说明该加新槽——**槽位表是随玩法演化的配置，不是封板圣旨**。
- **重要性判断在全系统中只出现一处**：卷压缩的保留取舍——且已被"事后提及统计"机械化。其余一切判断均为检测题（P3）。

## 12. 各层职责一句话总结（实现时迷路请回读）

> 状态表保证模型**不说错**，摘要保证模型**接得上**，原文保证模型**演得像**，检索偶尔**捞细节**，磁盘归档保证一切错误**可恢复**。
>
> 整个系统是一个 context 编译器：磁盘上的全量历史是源码，每轮编译出固定大小的最优 context 是产物，异步调用是编译 pass，RP 主模型是运行时。所有异步工作的唯一目的，是让那一次同步注入**又小又准**。
